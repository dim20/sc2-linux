# v0.8.0-docker — containers on the S905X4/SC2

Docker, containerd and runc support. The published kernel could not create
a container: it had no IPC namespace, no device or pids cgroup, no bridge
driver and no nftables plumbing. This release adds the container kernel
surface, and moves the optional filesystems to loadable modules so the
Image still fits the box's 48 MiB BOOT partition.

**Status: candidate, built and manifest-checked 2026-11-09.** The kernel
package was installed on the development box, cold-booted, and Docker ran
`hello-world` plus a bridge-network fetch. The stick image has not yet been
written to a stick and booted; that is the remaining hardware gate, listed
in `dist/TEST-CHECKLIST.md`.

## What changed since v0.7.3-wifi

### 1. Container namespaces and cgroups

Docker's `contrib/check-config.sh` listed the same gaps on the published
kernel that runc hits first:

- `IPC_NS` was missing because `init/Kconfig` makes it depend on
  `SYSVIPC || POSIX_MQUEUE`, and both were off. `unshare --ipc` returned
  `EINVAL`.
- `CGROUP_DEVICE`, `CGROUP_PIDS` and the other controllers were off, so
  runc could not enforce device or process limits.
- `BRIDGE`, `BRIDGE_NETFILTER` and the nftables expressions were off, so
  Docker could not create its default bridge.

The delta now enables `SYSVIPC`, `IPC_NS`, `POSIX_MQUEUE`, `USER_NS`,
`CGROUP_DEVICE`, `CGROUP_PIDS`, `CGROUP_PERF`, `CGROUP_HUGETLB`,
`BLK_CGROUP`, `BLK_DEV_THROTTLING`, `FAIR_GROUP_SCHED`, `CFS_BANDWIDTH`,
`NET_CLS_CGROUP`, `CGROUP_NET_PRIO`, `CGROUP_NET_CLASSID`, `BINFMT_MISC`,
`SECURITY_APPARMOR` and `SECURITY_YAMA`.

### 2. Container networking

`BRIDGE`, `BRIDGE_NETFILTER`, `BRIDGE_VLAN_FILTERING`, `VLAN_8021Q`,
`VXLAN`, `GENEVE`, `MACVLAN` and `IPVLAN` are built in. `NF_TABLES` and
its `inet`/`ipv4`/`ipv6`/`netdev` families, `NFT_COMPAT` (the
iptables-nft translation layer), the common `NFT_*` expressions, the
addrtype/IPVS/multiport/physdev/log matches, IPv6 NAT, `IP_SET` and the
IPVS protocol/scheduler set are enabled. `IP_SCTP` is on for telephony
containers.

### 3. Filesystems and storage

`BTRFS`, `XFS`, `CIFS`, `NFS` (v2/v3/v4), `F2FS`, `DM_THIN_PROVISIONING`,
`BLK_DEV_NBD` and `HUGETLBFS` are available. The USB-serial adapters Home
Assistant needs (CP210x, CH341, FTDI, PL2303, OPTION, CDC-ACM) are built
in.

### 4. The Image fits the 48 MiB BOOT partition again

Building these filesystems into the Image pushed it over the installed
48 MiB ext4 `BOOT` partition's real budget (about 38.9 MiB once the old
Image is removed). The heavy optional filesystems and storage targets are
therefore modules:

- `btrfs`, `xfs`, `cifs`, `nfs` and their dependencies
  (`zstd`, `xxhash`, `xor`, `raid6_pq`);
- `dm-thin-pool`, `dm-persistent-data`, `dm-bio-prison`, `nbd`;
- `md4` for CIFS NTLM.

The final Image is **37,021,704 bytes (35.3 MiB)**.

Two options stay built in:

- `ccm` — selected by CIFS and used by mac80211 through the crypto API;
- `f2fs` — the vendor tree defines `trace_android_fs_*` in ext4 without
  `EXPORT_SYMBOL`, so an `f2fs.ko` cannot resolve them and refuses to load.

### 5. The module set is replaced, not merged

The image build now removes the previous `*.ko` set in
`/lib/modules/<uname -r>/extra/` before copying the new one. Without that,
`ccm.ko` from v0.7.3 would have survived as a stale module even though CCM
is built in now.

The image ships 28 loadable modules. The kernel package is still
Image-only; the modules ship in the OS image.

### 6. Installer and smoke-test hash

`install-to-emmc.sh` and `smoke-test.sh` now expect `ee6433ad…`. Without
this, the installer would have refused the new kernel.

## What did not change

- The text console on HDMI and serial, HDMI audio, the clock fallback,
  the hostname fix, the eMMC installer and the 24-check smoke test.
- The device tree.
- The `sc2-kernel` package is still Image-only. A kernel-package update
  must be paired with the matching module set from the same release.

## Hardware test

The kernel package was installed on the development box (the v0.7.3-wifi
eMMC system), not flashed:

- `dpkg -i linux-image-sc2_5.4.210-sc2-docker1_arm64.deb` archived the old
  kernel (`e8e4dda1…`) and wrote the new Image to p1; the hash was read
  back from storage and matched `ee6433ad…`.
- Cold boot: `Linux sc2 5.4.210-ga3aaaa5b0e64-dirty #1 SMP PREEMPT`.
- `unshare` succeeded for ipc, user, pid, uts, net, mount and cgroup.
- `btrfs`, `xfs`, `cifs`, `nfsv4`, `dm-thin-pool`, `nbd` and `md4` loaded.
- Docker 26.1.5, containerd 1.7.24 and runc 1.1.15 installed from Debian
  trixie; cgroup v2 and overlay2; `docker run --rm hello-world` printed
  the expected message; a container fetched `http://example.com` over the
  default bridge, proving DNS, NAT and the bridge path.
- WiFi: `rtw_8822cs` loaded firmware 9.9.6, `wlan0` appeared and
  `iw dev wlan0 scan` returned BSS entries. The image still ships no
  credentials.

## What is still broken, or needs care

- **`iptables-nft` does not work on this 5.4 kernel.** Debian 13's
  iptables 1.8.11 creates nftables chains but cannot append rules to them:
  `RULE_APPEND failed (No such file or directory)`. It uses nftables chain
  IDs that this vendor kernel predates. Docker's daemon fails with
  `unable to add return rule in DOCKER-ISOLATION-STAGE-1 chain` until the
  alternatives are switched to the legacy backend:

  ```sh
  update-alternatives --set iptables  /usr/sbin/iptables-legacy
  update-alternatives --set ip6tables /usr/sbin/ip6tables-legacy
  systemctl restart docker
  ```

  The kernel's legacy backend is built in and works. Debian trixie does
  not install `arptables-legacy` or `ebtables-legacy` by default; Docker
  does not need them for the bridge driver.

- **The Docker CLI is a separate package on trixie.** Install both:

  ```sh
  apt install docker.io docker-cli
  ```

- **No WiFi credentials are shipped.** The template is deliberately empty.
  Add a network block with `wpa_passphrase`, then restart
  `wpa_supplicant@wlan0`.

- **The stick image has not yet been stick-booted.** The hardware test
  above used the kernel package on an existing box. Follow
  `dist/TEST-CHECKLIST.md` before publishing.

- **The 48 MiB BOOT partition is still the installer's default.** It is an
  arbitrary choice, not a hardware requirement; the U-Boot environment at
  116 MiB allows a p1 up to about 76 MiB. Growing it needs a reinstall,
  not an in-place update, so it is left for a later "big" release.
